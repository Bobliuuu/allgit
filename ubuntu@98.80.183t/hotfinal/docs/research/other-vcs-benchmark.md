# allgit `vcs` vs other version control systems (100k-file benchmark)

Status: **measured, one machine, shared and noisy**. Same three 100k-file datasets as `scripts/bench_scale.sh`
(`datagen flat|deep|binary 100000`, seed 42), run against `vcs` (this repo at `28e2980`) and every other
open-source VCS that could be obtained without system packages or sudo. Nothing below is estimated: every number is a
median of the raw runs stored in [other-vcs-raw/](other-vcs-raw/) (one JSON line per run: wall ms, CPU ms, rc, load1
before and after).

## What was run

| item | value |
|---|---|
| machine | Lambda box `lambda-final`: AMD EPYC 7J13, 30 cores, 216 GiB RAM, ext4 on virtio disk, kernel 6.8.0-1046, Ubuntu 22.04. **Shared with other jobs**; load1 over the first pass was 3.5 to 37.3 (median 6.7), over the short-cell pass 1.1 to 15.5 (median 4.1) |
| date | 2026-11-01 |
| driver | [`scripts/bench_other_vcs.py`](../../scripts/bench_other_vcs.py) (`<layout> 100000 5`), summary: [`scripts/summarize_other_vcs.py`](../../scripts/summarize_other_vcs.py) |
| method | per cell, runs are **interleaved round-robin over the tools** (run 1 of every tool, then run 2, ...); prep is untimed; each timed command runs in a fresh `bash -c`; wall time from the parent's clock, CPU time = user+sys from `wait4` rusage of the command and its waited-for children; warm page cache; runs per cell 5, cut to 3 when the first run took more than 90 s and to 1 when it took more than 600 s |
| datasets | each tool gets its own copy generated by `datagen` straight into its working directory |
| history | 50 commits per tool (initial commit, a 1% modification commit, then 48 one-file commits), the same recipe as `bench_scale.sh` |
| checkout cell | move from the first commit to the 50th (1,000 plus 48 files differ); the prep (untimed) goes back to commit 1 |
| status 1% modified | every 100th file in sorted order rewritten in place (1,000 files) |

Short cells (status, log, checkout) were **re-run in a second pass** (`*-short.jsonl`) at much lower machine load
(load1 1.1 to 15.5) and with a 0.5 ms wait poll. The first pass polled for process exit every 20 ms, so its sub-second
values are quantised to multiples of 20 ms and are not used; they remain in the raw files. Add, commit and clone
come from the first pass. The first pass ran the three layouts **concurrently** with each other and with other agents'
jobs on this box (load1 3.5 to 37.3); the interleaving makes the tools suffer alike, but absolute times are inflated
compared with a quiet machine (compare `git add` here, 24 s on flat, with 9.6 s in the README table that was taken on a
quieter day).

### Commands timed

| workflow | git | hg | svn | fossil | bzr (breezy) | pijul | vcs |
|---|---|---|---|---|---|---|---|
| add (fresh index) | `git add .` | `hg add -q .` | `svn add -q --force .` | `fossil add .` | `brz add -q .` | `pijul add -r .` | `vcs add .` |
| commit (all staged) | `git commit -q -m c` | `hg commit -q -m c` | `svn commit -q -m c` | `fossil commit -m c --no-warnings` | `brz commit -q -m c` | `pijul record -a -m c` | `vcs commit -m c` |
| status | `git status --porcelain` | `hg status` | `svn status` | `fossil changes` | `brz status` | `pijul diff --short` | `vcs status` |
| log, 50 | `git log --oneline -n 50` | `hg log -l 50` | `svn log -l 50` | `fossil timeline -n 50` | `brz log -l 50 --line` | `pijul log --limit 50` | `vcs log -n 50` |
| checkout (commit 1 -> 50) | `git checkout -q main` (from branch `side`) | `hg update -q -r tip` (from rev 0) | `svn update -q` (from `-r 1`) | `fossil update trunk` (from commit 1) | `brz revert -q -r -1` (from `-r 1`) | **no equivalent measured** | `vcs switch main` (from `side`) |
| full clone | `git clone -q file://...` | `hg clone -q --pull` | `svn checkout -q file://...` | `fossil clone` + `fossil open` | `brz branch -q` | `pijul clone` | `vcs clone <dir remote>` |

Important semantic differences, so the cells are not all the same work:

* **`add` only registers paths in hg, fossil, bzr and pijul** (they hash the content at commit time). Git and vcs hash and store
  the content at `add`; svn's `add` is slow because it also writes a pristine copy per file into `.svn`. The fair cell is **add + commit**
  (sum of the two medians, below).
* Fossil and Subversion `commit` is a **server-style transaction** (SQLite repository / FSFS revision) and has to read and write all 100k files.
* Hg `clone --pull` was used to match git's `file://` transfer (the default local hg clone hardlinks the store).
  Git's default path clone (hardlinks) is also listed.
* Pijul has no cheap "switch between two states of a working copy" command comparable to the others (`pijul reset`
  restores the last record; channel fork + switch is a different workload), so that cell is not measured.
  Pijul's `log` shows changes (patches), not snapshots.
* Subversion's `log` and `checkout` talk to a local repository over `file://` (no network).
* Git LFS and Git `sparse-checkout`/`sparse-index` were not measured: the datasets have no large binaries to offload and no
  directory subset is defined. Partial and shallow clone are measured as clone-only rows below.

## What this shows

* **Commit of 100k files**: vcs 0.3 to 1.1 s, git 0.8 to 21 s, Mercurial 55 to 98 s, Breezy 49 to 99 s, Pijul 16 to 25 s,
  Subversion 5 to 15 min, Fossil about 17 to 18 min (one run each, over 600 s). Sum of add + commit, vcs is the fastest on all three layouts here, but
  these runs were at high machine load and the vcs run uses several threads; do not read the ratio more precisely than "several times".
* **status**: git with the built-in fsmonitor + untracked cache is the fastest of everything (28 to 127 ms), with plain git
  and vcs next (about 110 to 150 ms flat/binary; on deep vcs 442 ms vs git 1,057 ms). Hg, Fossil, Subversion and Breezy take
  0.3 to 9 s; Pijul 3.5 to 8 s (it re-hashes the whole tree; 25 to 51 s of CPU).
  Mercurial's very first status after a commit took 26 to 49 s once per run set (dirstate rebuild); the median hides it.
* **log (50)**: git, Fossil, Subversion and vcs are all between 6 and 20 ms; Mercurial about 260 ms (Python start-up), Breezy about 170 ms, Pijul 150 to 260 ms.
* **checkout (1,048 files differ)**: git and vcs are within about 30% of each other (347 to 527 ms); Mercurial 0.75 to 1.6 s; Subversion 2.5 to 10.8 s;
  Fossil 12 to 18.6 s; Breezy 8.9 to 12.6 s.
* **clone**: vcs 4 to 9 s, git 6 to 12 s, Fossil 18 to 25 s, Pijul 23 to 56 s (CPU up to 750 s), Mercurial 54 to 63 s, Subversion 57 to 97 s.
  Breezy took about 880 s on flat and binary (one run) and did not finish deep: I stopped it after 1,849 s.
* **disk**: git has the smallest store on the text layouts (54 to 68 MB after the first commit), then vcs, Fossil and Breezy (75 to 114 MB); on binary all but Mercurial and Pijul are within 420 to 480 MB. Mercurial's store is 424 to 824 MB by `du` (block rounding of per-file revlogs, see above). Subversion's repository is 95 to 125 MB on the text layouts, but its `.svn` pristine copies add 460 to 495 MB, about another working copy.

## Caveats

* One machine, shared, high and variable load (see the load column in the raw files); the three layouts' long cells ran concurrently.
  The status/log/checkout cells come from a second, quieter pass; they are not from the same minutes as add/commit/clone.
* The `vcs` binary uses several threads where git, hg (mostly), svn, fossil and bzr use one; CPU columns are provided for that reason.
* The driver is the author's, not a vendor-supplied benchmark; each tool was run with default settings (plus the git-fsmonitor variant). Tuned configurations
  (for example Mercurial's `fsmonitor` and `largefiles`, Subversion over `svn://`, Fossil `--hash` or `mtime-changes` settings) were not tried.
* Subversion was not run through a server, so network cost is absent; Fossil is a single SQLite file whose commit is a transaction.
* `status 1% modified` measured only content changes (no adds or deletes).
* Only the first commit's store size is "fresh"; the size after 50 commits depends on how each tool's history is stored (git auto-gc).
* Sapling and Jujutsu are covered separately in [sapling-benchmark.md](sapling-benchmark.md) and [jujutsu-benchmark.md](jujutsu-benchmark.md) (different machine, git 2.43.0, so not mixed into these tables). Not tried: Plastic SCM, Git LFS, git with `sparse-index` / `core.fsyncMethod` variants, Perforce (see [perforce-benchmark.md](perforce-benchmark.md)), walgit (see [walgit-benchmark.md](walgit-benchmark.md)).
* A first attempt on the AWS "quiet" box was abandoned because the disk was saturated by other jobs (I/O pressure above 50%, `git add` stalled for minutes); nothing from it is used.
  Toolchain notes: Pijul's `cargo install` without a version picks 0.15.0 and fails at libsodium; `1.0.0-beta.26` with conda-forge headers builds.

## Reproduce

```sh
# on a Linux box, with datagen and vcs built (cargo build --release --workspace --bins)
OV_ROOT=~/rt/ov python3 scripts/bench_other_vcs.py flat 100000 5            # all tools, all cells
OV_CELLS=status_clean,status_1pct,log50,checkout_1pct OV_TAG=-short \
  python3 scripts/bench_other_vcs.py flat 100000 5                           # only the short cells (setup still runs)
python3 scripts/summarize_other_vcs.py docs/research/other-vcs-raw/flat.jsonl
```

`OV_ROOT` holds `bin/{vcs,datagen}`, `wrap/{hg,brz,svn,svnadmin}` (tiny sh wrappers that put each conda environment first on `PATH`),
`tools/fossil/fossil`, `tools/pijul/bin/pijul`. Setup used: micromamba `create -n svn|hg|bzr -c conda-forge subversion|mercurial|breezy`, the Fossil tarball above, and
`cargo install pijul --version 1.0.0-beta.26`.
