# Per-command scoreboard: vcs against git, Perforce and walgit

Generated by `scripts/command_scoreboard_render.py` from the JSON in `docs/research/data/command-scoreboard/` (`scripts/command_scoreboard.py`, `scripts/command_scoreboard_p4.py`) and, for walgit, `docs/research/data/walgit-full-boxc/`. Images: `docs/img/scoreboard-git.svg`, `scoreboard-p4.svg`, `scoreboard-walgit.svg`.

## How to read this

* **Verdict rule (fixed before looking at results).** ratio = vcs / reference, the median over the interleaved rounds of the per-round wall ratio and of the per-round CPU ratio (CPU = user+sys of the command from `wait4`; for p4 also the p4d CPU delta; for walgit the sum of client, front-server and object-store CPU). **WIN**: both ratios <= 0.90. **LOSS**: both ratios >= 1.10. **TIE**: everything else, including any cell whose wall-clock median difference is under 2 ms (process start-up noise). A TIE where only one of wall/CPU is beyond the band is flagged `mixed` in the note.
* **MISSING**: the doc table says vcs has no equivalent (listed, not omitted). **NOT-MEASURED**: vcs has the command but no scenario was run, or the scenario failed (non-zero exit), or the reference tool was not usable; the reason is in the note. No number is invented for those.
* Rows marked `*` are extra scenarios that are not a row of the doc table under that spelling.
* Several doc rows share one scenario (for example `git add .` and `git add -A`). The scenario is stated in the JSON under `cmds`.

## Where and how it was run

* Machine: ip-172-31-8-192 (AWS c6i.4xlarge timing box E, 16 vCPU), run 2026-11-02, vcs release build of `origin/main` 8da0be2, git: `git version 2.43.0`, vcs: `vcs 0.1.0`, dataset `datagen flat 100000` (seed 42). Timing under `flock ~/bench.lock`, one group at a time, tools interleaved per round in random order, warm cache.
* **Load caveat**: the box is shared; load1 was sampled at the start and end of each group and is low but not zero (per group: clean: load1 1.5->2.1; dirty: load1 2.1->1.9; fresh: load1 2.0->1.5; remote: load1 2.1->1.7; small: load1 1.9->1.8; untracked: load1 1.9->1.9). Other agents' builds can run outside the lock. Wall times for slow cells carry that noise; the per-round load is in the JSON.
* **Before column**: the earlier run of the same scenarios (`docs/research/data/command-scoreboard-prev/`, same box, earlier the same day; the vcs build is not recorded in that data, it predates the speed fixes merged since) is kept for comparison. It is the previous wall ratio and verdict, not a re-measurement; a cell with `n/a` had no comparable previous result.
* Runs per cell: 5 (3 for slow cells), the `n=` in each row says how many. Medians only; min/max are in the JSON. No significance test: the 10% band is a practical threshold, a cell at 0.95 to 1.05 is not distinguishable from noise with 3 to 5 rounds.
* Perforce: `Rev. P4/LINUX26X86_64/2025.2/3086021 (2026/10/05).` client, `Rev. P4D/LINUX26X86_64/2026.1/3089746 (2026/10/07).` server (binaries copied from the earlier Perforce benchmark, SHA256 re-checked against docs/research/perforce-benchmark.md), p4d on loopback, journal off, no log, free tier, a fresh server root for the initial add/submit; 1 user, 1 client. p4 is client/server, vcs is local: the comparison is p4 client plus server work against what vcs does locally; the vcs side of submit also publishes to a local-path remote. **p4 CPU is a lower bound**: it is the p4 client plus the p4d process's own and reaped-children CPU read from /proc in 10 ms ticks, so server CPU below the tick is largely missed (tiny commands show about 2 ms = client only). Treat p4 CPU ratios of small commands as unreliable; p4 wall includes the server round trip and is the better number. p4 `grep` failed on this server (revision limit 10000 for `//...`), `p4 verify` printed nothing in 3 ms; both are NOT-MEASURED. Cells with n=2 or 3 (clone, sync, submit, add, files, have) are small samples (each takes seconds to minutes).

Not run, stated plainly: deep and binary layouts (this scoreboard is flat 100k only), any real network or S3, multi-user Perforce, interactive/continuation commands.

Data groups present in this render: clean, dirty, fresh, remote, small, untracked, p4 (of fresh, clean, dirty, untracked, small, remote, p4). Rows of a missing group show NOT-MEASURED.
