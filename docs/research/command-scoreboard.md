## How to read this

* **Verdict rule (fixed before looking at results).** ratio = vcs / reference, the median over the interleaved rounds of the per-round wall ratio and of the per-round CPU ratio (CPU = user+sys of the command from `wait4`; for p4 also the p4d CPU delta; for walgit the sum of client, front-server and object-store CPU). **WIN**: both ratios <= 0.95. **LOSS**: both ratios >= 1.05. **TIE**: everything else, including any cell whose wall-clock median difference is under 2 ms (process start-up noise) or smaller than MAD(vcs)+MAD(reference) of the wall times. A TIE where only one of wall/CPU is beyond the band is flagged `mixed` in the note.
* **MISSING**: the doc table says vcs has no equivalent (listed, not omitted). **NOT-MEASURED**: vcs has the command but no scenario was run, or the scenario failed (non-zero exit), or the reference tool was not usable; the reason is in the note. No number is invented for those.
* Rows marked `*` are extra scenarios that are not a row of the doc table under that spelling.
* Several doc rows share one scenario (for example `git add .` and `git add -A`). The scenario is stated in the JSON under `cmds`.

Every other cell, and the machine/build line below, is from the 845610a run above; the `before` column is unchanged. Source: `remeasured` in the `meta` of `git-clean.json` and `git-dirty.json`.

* Machine: ip-172-31-0-32 (AWS c6i.4xlarge timing box c, 16 vCPU), run 2026-11-04, vcs release build of `origin/main` 845610a, git: `git version 2.43.0`, vcs: `vcs 0.1.0`, dataset `datagen flat 100000` (seed 42). Timing under `flock ~/bench.lock`, one group at a time, tools interleaved per round in random order, warm cache.
* **Load caveat**: the box was idle apart from the harness (every timed round waits for load1 < 1.0, forced releases are in the JSON `quiet_gate_waits`); load1 was sampled at the start and end of each group and is low but not zero (per group: clean: load1 1.3->1.0; dirty: load1 1.0->1.0; fresh: load1 1.0->1.0; remote: load1 1.0->1.0; small: load1 1.0->1.0; untracked: load1 1.0->1.0). Other agents' builds can run outside the lock. Wall times for slow cells carry that noise; the per-round load is in the JSON.
* **Before column**: the earlier run of the same scenarios (`docs/research/data/command-scoreboard-prev/`, box E, 2026-11-02, build 8da0be2) is kept for comparison. It is the previous wall ratio and verdict, not a re-measurement; a cell with `n/a` had no comparable previous result.
* Runs per cell: 9 (fewer for slow cells), the `n=` in each row says how many. Medians only; min/max are in the JSON. Significance: a gap smaller than MAD(vcs)+MAD(reference) of the wall times is a TIE (`within noise`), as is anything inside the 5% band; a cell at 0.95 to 1.05 is a TIE.
* Perforce: `Rev. P4/LINUX26X86_64/2025.2/3086021 (2026/10/05).` client, `Rev. P4D/LINUX26X86_64/2026.1/3089746 (2026/10/07).` server (binaries copied from the earlier Perforce benchmark, SHA256 re-checked against docs/research/perforce-benchmark.md), p4d on loopback, journal off, no log, free tier, a fresh server root for the initial add/submit; 1 user, 1 client. p4 is client/server, vcs is local: the comparison is p4 client plus server work against what vcs does locally; the vcs side of submit also publishes to a local-path remote. **p4 CPU is a lower bound**: it is the p4 client plus the p4d process's own and reaped-children CPU read from /proc in 10 ms ticks, so server CPU below the tick is largely missed (tiny commands show about 2 ms = client only). Treat p4 CPU ratios of small commands as unreliable; p4 wall includes the server round trip and is the better number. p4 `grep` failed on this server (revision limit 10000 for `//...`), `p4 verify` printed nothing in 3 ms; both are NOT-MEASURED. Cells with n=2 or 3 (clone, sync, submit, add, files, have) are small samples (each takes seconds to minutes).

Not run, stated plainly: deep and binary layouts (this scoreboard is flat 100k only), any real network or S3, multi-user Perforce, interactive/continuation commands.

Data groups present in this render: clean, dirty, fresh, remote, small, untracked, p4 (of fresh, clean, dirty, untracked, small, remote, p4). Rows of a missing group show NOT-MEASURED.

## Remaining losses and their causes

Causes are from the code and the timings (wall vs CPU), not from profiles taken in this pass.

| loss | cause |
|---|---|
| (fixed, TIE) git `bundle verify` | was 376 ms: the default re-hashed the whole pack. The default is now the header-only check (`verify_quick`, what git does); `--full` keeps the whole-pack hash and decode, and `fetch`/`clone` always run it. 1.3 ms against 2.0 ms is below the 2 ms floor. |
| git `init`, `init proj`, `branch -m` | wall loss of ~10 ms with CPU within 1.2x (branch -m 1.75x CPU): fixed process start-up, store directory creation and fsync of the new ref, below what git does lazily. |
| (fixed) git `grep -F -- src`, `ls-files`, `ls-files -s` | `scan_tracked` fully decoded the AGI5 index (100k entries) before printing; it now walks the mapped blocks. `ls-files` and `ls-files -s` are WINs, `grep -F` a TIE (wall 0.37, CPU 0.99). |
| git `ls-tree -r --name-only` (`ls-files --rev`) | not re-measured. Streaming the tree walk into the output (no entry list) measured 0.99 wall on the same box, so the cost is tree decode, not the list; not shipped. |
| git `switch --detach`, `checkout --detach` | not re-measured. Detach already skips the untracked walk; full-tree stat pass plus index decode and rewrite, as git. A port of the rest of `checkout` onto it measured slower (a second index decode) and was dropped. |
| git `add -u`, `commit -a` | still a LOSS after skipping the untracked walk (1.12 / 1.37 and 1.29 / 1.40): the status pass finds the changed files, then `add` reads, hashes and writes them and patches the index in a second pass; fusing the two would hash once. |
| p4 `submit` (1 file), `opened`, `delete`, `revert`, `diff` | p4 is a thin client to a warm p4d (4 to 9 ms wall); vcs runs the work in-process after process start-up and a status scan, and `submit` includes publishing to the remote. p4 CPU is a lower bound. |
| p4 `sync path@rev` | 1.17x wall: vcs writes the files of a computed commit; p4d streams already stored revisions. |

jj and Sapling: no losses in the measured flat 100k cells, see `docs/research/jj-sl-final.md`. walgit: no losses.
