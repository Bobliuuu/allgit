# 10x opportunities: ranked list, prototypes, and what did not pan out

Scope: research plus prototypes, no AWS, no spending. Rule: speed over storage; ties go to speed.
Prototype code: `crates/vcs-repo/examples/snapbench.rs` (example only, not wired into any command, so nothing changes by default).

## Honest measurement caveat

macOS arm64, 10 cores, **load average 57-83 from other agents the whole session**. Every wall number is inflated and noisy; the kernel-bound ones (file creation) most of all. Numbers below are single runs unless stated and are good for ratios of order of magnitude, not for a scoreboard. 100k-file flat tree (`datagen flat 100000`, 391 MB, 100,054 files). Anything marked "not measured" was not.

## What the code already does (so these are not re-proposals)

Block-indexed index with point patch (`index_file.rs`), lazy tags (#481), lock-free pack-index cache, group commit, commit-graph on import/gc, journal with one preallocated `sync_data`, parallel clone/checkout, fsmonitor watcher, per-file stat cache with ctime. The remaining losses in `command-scoreboard.md` are mostly small absolute numbers (ref ops 5-6 ms vs git 1.4 ms; one `fsync`-sized gap) or p4 server round trips. The big levers left are therefore **kernel-bound file creation**, **whole-index decode**, and **durability policy**.

## Measured prototypes

| # | What | Before | After | Gain |
|---|---|---|---|---|
| P1 | Create 100k x 4 KiB files, 1 thread: tmp file + rename + path stat (what `RealFs::write` does) vs `O_EXCL` at the final path + `fstat` (valid when the path is known absent, i.e. clone / fresh checkout) | 49.1 s, 37.0 s (2 runs) | 18.6 s (1 run) | **2.0-2.6x** |
| P1 | same, 8 threads | 16.8 s | 12.7 s | 1.3x (kernel/APFS directory lock bound) |
| P2 | Whole materialized tree (100,054 files) duplicated with one `clonefile(2)` on the directory | `vcs clone` of the same repo: 17.4-26.1 s wall, 15 s sys (3 runs, same load era); `cp -c -R` 30-40 s | 1.43-1.67 s (5 runs) | **~12-15x vs vcs clone**, ~25x vs `cp -c -R` |
| P3 | Re-stamp a cloned tree's index (ctime changes on clone; mtime/size are preserved): lstat of 100k files | 2.45 s (1 thread) | 0.22 s (8 threads) | 11x; makes P2 + restamp ~1.9 s total |
| P4 | Point lookups into an mmap'd fixed-width record file vs read + decode-all (100k records, 1000 lookups) | 1.95 ms | 0.34 ms | 5.7x on this toy; real index decode today is **14.7 ms wall / 30.8 ms CPU for 100k entries** (`index_cost`, loaded), encode 7.1 ms |

Caveats that matter: P2's baseline was not interleaved in the same second with the clone (load drifted 24 to 59); `clonefile` on a directory is documented as discouraged by Apple and a forum report of 77k files taking about 2 minutes exists, but here it took 1.5 s on the internal SSD volume, so the result depends on volume and load. Source and destination must be on the same APFS volume (Linux: `FICLONE`/`cp --reflink` needs XFS reflink=1 or btrfs, so ext4 EBS boxes get nothing). P1 skips tmp+rename, so a crash mid-write leaves a partial file at the final path; only acceptable for paths the index does not yet trust (fresh clone, and write the index last, which the code already does). P4 is a toy: it shows the ceiling for avoiding decode, not a design.

Also seen while measuring: `rm -rf` of a 100k-file tree took 87 s under this load (kernel unlink bound), so any scheme that makes trees cheap to create also makes CI cleanup the next bottleneck; a "trash then unlink in background" step (rename the tree away, delete in a detached process) turns that into one rename.

## Ranked ideas

Gain column is expected gain on OUR measured cases, not the source's headline.

| Rank | Idea | Source | Expected gain on our losses/wins | Evidence | Effort | Risk |
|---|---|---|---|---|---|---|
| 1 | **Materialized-tree snapshot cache**: after a checkout of root tree T, keep a COW snapshot (`clonefile` / `FICLONE`) keyed by T; any later clone/switch/worktree add of T (CI job, agent worktree, switching back) is one clone call + parallel restamp | [clonefile(2)](https://developer.apple.com/forums/thread/784446), [git-fast-worktree](https://github.com/orf/git-fast-worktree), [git-cow](https://docs.rs/crate/git-cow/0.4.0), Eden's materialized/non-materialized model (`docs/research/virtual-fs.md`) | clone/sync/worktree add of 100k files: 10-15x (P2+P3). Directly targets `p4 sync` 5.1x loss and the CI fan-out workload. Zero effect on first clone on a cold machine. | P2, P3 | 2-3 weeks (snapshot store, invalidation by tree id, restamp, GC of snapshots, same-volume check, Linux reflink fallback) | Disk (COW makes it free until files change; speed over storage rule says accept); stale snapshot if user edits the snapshot (never hand out the snapshot itself, only clones of it); directory clone slow on some volumes |
| 2 | **Direct create on fresh checkout**: `O_EXCL` at final path, `fstat` the fd, no rename, no path stat; use `fcopyfile`/`copy_file_range` when the source is an uncompressed cache | git does tmp-less writes in `checkout_entry`; P1 | clone/switch of N files: 2.6x single-thread, 1.3x at 8 threads (P1). Cuts sys time (clone was 15 s sys) | P1 | 2-3 days (a `RealFs::create_fresh` used only by clone and by checkout when the path was just removed or never existed) | Partial file on crash at a not-yet-indexed path; mitigated by writing the index last and by re-verifying on next status |
| 3 | **Parallel first scan with per-directory fan-out** (stat + hash), plus restamp-from-clone | scalability.md finding 10 ("parallel first scan is the only lever; not built"); P3 | first `status` after import: 22 s (300k files) and 5.8 s (100k here) ; lstat part drops 11x with 8 threads; hashing is already cheap (user 0.5 s) so the cap is the sum of syscalls | P3, `time` of first status in this run (sys 7.5 s vs user 0.5 s) | 3-5 days | Low; only ordering of index inserts |
| 4 | **Zero-copy mmap index** (fixed-width records + offset table, no decode; `status` compares stat in place; patch writes touched pages only) | [rkyv](https://github.com/rkyv/rkyv), Sapling's dirstate/treestate (mmap'd), git index v4 limits | status/add/restore on 100k: removes 14.7 ms wall / 30.8 ms CPU decode and 7 ms encode per command; the p4-small-ops losses (5-19x, absolute 24-47 ms) are where this shows. Realistic 2-3x on those cells, not 10x. | P4 (toy), `index_cost` | 3-4 weeks (format AGI5 behind feature, migration, patch path) | Format risk, alignment/endianness, mmap + concurrent writer semantics (must write new file + rename) |
| 5 | **Deferred-durability ref ops**: branch/tag/switch -c return after the journal write without `sync_data`; durability barrier at next object-bearing command or process exit (git does not fsync refs by default) | git `core.fsync` defaults; jj/Sapling also do not fsync ref moves on every command | `branch/tag/branch -d/-m` 4.3-5.8x wall loss vs git (6.5 ms vs 1.4 ms; CPU already 1.3-1.8x, so the gap is the sync). Would reach ~parity (4-5x on these cells). Absolute gain about 5 ms/op. | scoreboard LOSS rows, journal.rs sync points | 2-4 days | Real durability change on power loss (op log could lose last ref moves, never corrupt: journal replay already covers it); needs a decision, not just code |
| 6 | **Background trash-and-delete** for tree removal (`rename` to `.vcs/trash`, unlink in detached process) | Eden/Buck2 do async cleanup | `switch`/`reset --hard`/`clean -fd` that delete many files: delete cost moves off the critical path (rm of 100k took 87 s loaded) | measured rm | 2 days | Disk space transiently held; leftover on crash (GC at next run) |
| 7 | **Prefetch from the zone profile** (already have profile): warm blobs of predicted next zones into the page cache / pack mmap during idle, and issue pack range GETs in parallel for remote fetch | [Scalar background prefetch](https://git-scm.com/docs/scalar), Eden prefetch | Remote clone/sync latency: not measured here (no network). Local warm-cache wins are likely <2x | none local | 1-2 weeks | Wasted bandwidth |
| 8 | **S3 Express One Zone + parallel range GETs of packs + HTTP/2 multiplexing** | [S3 Express](https://aws.amazon.com/s3/storage-classes/express-one-zone/), range GET parallelism | Remote-only; single-digit ms first byte vs tens for S3 Standard, pack GET throughput scales with parallel ranges. Cannot measure (no AWS allowed). | none | 1-2 weeks | Cost (Express charges per request differently), single AZ |
| 9 | Git-style multi-pack-index + geometric repack in `gc` | [git multi-pack-index](https://git-scm.com/docs/multi-pack-index), [git repack --geometric](https://git-scm.com/docs/git-repack) | `gc` 1.8x loss (1127 ms vs 619): incremental repack avoids rewriting everything; 2x at best | scoreboard `git gc` | 1-2 weeks | Compaction correctness (model tests exist) |
| 10 | Persistent trees (prolly / Merkle search tree) so a tree diff is O(changed) regardless of layout | [Dolt prolly trees](https://docs.dolthub.com/architecture/storage-engine/prolly-tree) | `ls-tree HEAD` 19x loss (33.8 vs 1.8 ms) is not a tree-shape problem, it is whole-tree decode/flatten; a mmap'd flat tree cache (idea 4 applied to trees) fixes it more cheaply | none | months | Format change, hash compat |
| 11 | io_uring batched open/write/stat for checkout on Linux | [io_uring](https://kernel.dk/io_uring.pdf) | Linux boxes only; could cut syscall count 3-5x on checkout; not measurable on this Mac | none | 2+ weeks | Kernel/seccomp availability, unsafe code |
| 12 | Zstd dictionaries / FastCDC chunking | [zstd dict](https://facebook.github.io/zstd/#small-data), [FastCDC](https://www.usenix.org/conference/atc16/technical-sessions/presentation/xia) | Storage-saving ideas; rule says speed wins ties; decode speed unchanged. Skip. | `vcs-compress-lab` exists | n/a | n/a |

Not pursued, with reason: Pijul/Darcs patch theory (merge semantics, not speed; exponential merge cases); Perforce-style server-side `have` tables (the p4 round trip is the thing we are beating); QUIC (thread-per-connection server is not the bound; unmeasured); LMDB/redb/fjall for the index (the block-patched file already avoids full rewrite; a KV engine adds fsync per txn); blake3 mmap hashing (hash user time was 0.5 s of a 5.8 s first status: not the bottleneck); FSEvents/fanotify watchers (fsmonitor exists).

Web research limits: search returned usable sources only for clonefile/worktree COW and for EdenFS/commit-graph; the rest of the links in the table are well-known primary docs cited from memory and were **not fetched** in this session.

## Recommended order

1 and 2 together (2 is the cheap first step and the foundation for 1), then 3, then 5 if the owner accepts the durability trade. Idea 4 is the biggest engineering item but only a 2-3x on small ops.
