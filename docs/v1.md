# V1 scope: what is in, what is partial, what is not

Honest status at the commit this file was written against. Every bullet points to a doc, test or source file; where
there is no test, it says so. Nothing here is a release promise: no tag or release exists yet.

## What V1 is

A version control system written from scratch in Rust; the core crates never use git or libgit2.

* **Zones**: a repository is a set of independently versioned zones (docs/zones.md, docs/architecture.md); a snapshot
  pins a consistent set of zone versions (docs/object-model.md).
* **Local-first**: all everyday commands work offline against a local store.
* **Native storage** (BLAKE3 object ids, packs) plus **directory and S3 remotes** and an HTTP server
  (docs/remote-packs.md, docs/s3.md, docs/server.md).
* **Operation log and undo**: `vcs op log`, `op undo`, `op restore` (docs/operations.md).
* **Merge layers**: text merge, structural merge, optional AI-assisted resolution (docs/merge.md, docs/assist.md).
* **Interop**: Git import/export and a git remote helper (docs/interop.md, docs/import-git.md), Perforce import
  (docs/import-p4.md).

## Not in V1, or only partial

**Remotes and storage**

* Only AWS S3 was measured on real cloud (docs/research/storage/s3-aws-results.md) and RustFS/MinIO are the tested
  S3-compatible servers (docs/gc.md, docs/s3.md). Cloudflare R2, Google Cloud Storage and Backblaze B2 are unmeasured;
  docs/research/storage/provider-comparison.md is a paper comparison. GCS has no ETag `If-Match` on PUT, so it needs
  a different backend (same file).
* Remote GC works only on directory remotes. S3 and the HTTP server are refused with an error (docs/gc.md, "Remote sweep").
* S3 has no conditional DELETE, so remote deletes are unconditional and safety rests on the tombstone handshake
  (docs/gc.md). That path is only exercised against directory and in-memory backends (`crates/vcs-remote/tests/gc_real.rs`).
* Remote compaction on S3 runs without `gc/lock`, because S3 has no trusted clock yet. The docs argue concurrent
  compactors are harmless (docs/gc.md, "Backends"); this needs independent review. Open decision below.
* Remote GC does not rewrite packs: a pack with any live object is kept whole (docs/gc.md).
* The sharded manifest is a model-checked prototype and a benchmark; it is not integrated into publish/fetch
  (docs/manifest-scaling.md, "The sharding gate", step 3). Until then, the doc recommends fewer than 8 concurrent
  publishers per repository. Cloud numbers for R2 are still owed.
* `vcs-server` rejects bodies over `max_body` (1 GiB for non-manifest objects) with 413, so a pack over 1 GiB
  cannot be uploaded through it (docs/server.md; `crates/vcs-server/src/server.rs`).

**Formats**

* Pack/index v3 (written by compaction, `vcs repack --format v3`) and v4 (opt-in, local only) cannot be read by older
  binaries; they fail with "bad index header" rather than misreading. There is no minimum-reader marker in the
  repository or remote that would warn an old client up front (searched docs and crates; none found).
  Rollback is `vcs repack --format v2` locally or re-compacting with `--pack-format v2` remotely (docs/object-model.md).
* v4 packs are refused for upload; network packs stay v2 (docs/object-model.md).

**Platforms**

* Windows is compile-checked in CI, never run; symlink checkout fails there with an error; hooks do not run
  (docs/architecture.md, docs/object-model.md, docs/hooks.md, docs/install.md).
* HFS+ has no test on a real volume. Only name-level protections exist (HFS+-ignorable code points are rejected,
  docs/security-review.md; case/normalization collisions are refused everywhere, docs/object-model.md).
  macOS APFS is the Mac-tested case.
* Not tested for Git interop: Windows, SHA-256 repositories, shallow clones, concurrent pushes from several clones
  (docs/interop.md). Git import skips symlinks; there is no LFS or partial clone for Git.

**Zones**

* `vcs zone apply` (split a directory into a zone) is not undoable by `op undo` and is not tested as such; it is one
  directory at a time and each call walks the whole root tree (about 170 ms per call at 4,000 files), with no batch
  mode (docs/zones-autodetect.md, "Limits"). Deleting a zone is likewise not restorable by `op undo` (docs/zones.md).
* Zone history after a split starts at the split.

**Assist**

* The OpenAI assist budgets (`VCS_ASSIST_MAX_REQUESTS`, `VCS_ASSIST_MAX_TOTAL_TOKENS`) are per process, and `vcs`
  starts one process per conflict, so there is no budget across a whole merge (docs/assist-openai.md).

## Format stability

What the code and docs establish today:

* The object format version is inside the hashed bytes; readers reject unknown versions (`DecodeError::Version`).
  The golden id test `golden_blob_id_is_stable` pins blob ids (docs/object-model.md).
* Pack v1 and v2 are read "forever" per docs/object-model.md; v3 and v4 are additive, can sit beside v2, and are
  rollback-able as described above.
* The format has already changed incompatibly twice: v1/v2 objects are rejected by the current v3 object format
  (docs/object-model.md, "Symlinks and portable paths"). There is no migration tool in this repository for that.

What may break before 1.0 (no promise made here): the object format version, index layouts (`AGI*` in
docs/benchmarks.md is local-only and was bumped without backward reads), remote manifest versions and the sharded
layout, the `--json` command outputs beyond the `"version":1` field, and any experimental flag. Because no minimum-reader
marker exists, a format change can surface as a read error on an old binary.

## Known performance gaps versus git

Source: docs/research/interleaved-comparison.md only (interleaved runs, AWS instance b, 8 vCPU, git 2.43.0, 3 runs at
100k files, machine not quiet, load 5-20; read its caveats before quoting anything). From that file, new build versus git, CPU ratio:

* Still slower than git: `status` without the watcher (about 1.2x to 2.1x CPU across layouts), `checkout` (about 1.5x to
  1.85x CPU at flat/binary 10k and flat 100k), and `log -n 50` at flat 100k (about 2x, 9 ms vs 4 ms).
* With `vcs watch` running, status is below git CPU in the non-noisy cells.
* Faster than git in that run: add and commit in all measured cells.
* 100k wall-time columns are described there as unreliable; deep and binary 100k cells are missing.

Other benchmarks (docs/benchmarks.md, docs/research/*-benchmark.md) were not re-verified for this page.

## Decisions pending the owner

1. **Pack v3 vs v4 as default.** Today v2 is the default for publish; v3 is written by compaction; v4 is opt-in and
   local only. Which becomes the default, and whether either ships in V1, is undecided (docs/object-model.md,
   docs/research/storage/delta-gate.md).
2. **S3 compaction lock.** Keep running remote compaction on S3 without `gc/lock` (current behavior, argued safe in
   docs/gc.md), or gate it until S3 has a clock and touch (issue #232 referenced in docs/gc.md).
3. Related, not yet decided in the docs: whether to add a minimum-reader marker before the first tag, and when to
   integrate the sharded manifest.
