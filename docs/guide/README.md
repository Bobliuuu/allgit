# vcs user guide

`vcs` is a version control system built around **zones**: parts of one repository that own a path prefix and have
their own history and branches. It keeps big binary files and many teams in one tree without making everyone
download everything.

Every command example in this guide was run for real on a Linux machine with a release build.
The output is pasted from the run. Where something could not be run, the text says so in italics.
Commit ids and timestamps will differ on your machine.

## Status in one paragraph

This is early software. Local work (commits, branches, merge, rebase, undo, zones, snapshots, chunking, packs) is
tested the most. Directory, S3 and vcs-server remotes work. Locks are advisory. Perforce import is fixture-tested only.
Windows is compile-checked only. There is no stable on-disk format promise yet. For design, see
[../architecture.md](../architecture.md); for the repository overview, the top-level README.

## Reading order

New to `vcs`: chapters 1 to 3. Working in a team: 4, 5 and 8. Moving from Git: 7. Running a server: 10 and 11.

## How the examples were made

A script ran each chapter's commands in a fresh directory and recorded the output. The binary was
`cargo build --release --workspace` from the same commit as this guide. Structural merge used a second build with
`--features structural`. The S3 example used a local `moto` server. Identity came from `vcs config set --user`.
The command reference is generated by `scripts/gen_cli_reference.sh`, and a test fails if it is stale.
